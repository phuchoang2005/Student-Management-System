## Findings

- **F1 — Host changed from every v0.0 baseline: 2 physical CPU cores here vs. 4 on the v0.0 host.** Per `05-baseline-and-reporting.md` §1.1, a host change alone is grounds to not treat this as a clean baseline-quality comparison. It plausibly explains some across-the-board latency inflation and is the leading suspect for why `BM-XC-003`'s throughput ceiling only moved modestly (~34→~40-45 req/s) despite the pool tripling (10→30) *and* `IP-04` cutting `BM-ENR-002`'s own per-request cost substantially — CPU, not the connection pool, plausibly becomes the binding constraint at high concurrency on a 2-core host. Does **not** explain F2 below, which is root-caused independently of host capacity.
- **F2 — A real, evidenced regression: the combined-query shape Sprint 9 introduced for search costs more than the pre-fix `LIKE` scan for common search terms, and even for the no-filter control.** `SpringDataStudentRepository.search`/`SpringDataBookRepository.search` (`student/internal/SpringDataStudentRepository.java:23-33`, `book/internal/SpringDataBookRepository.java:28-37`) each collapse the filtered-search, no-filter, and cursor-continuation cases into one parameterized `@Query` with `OR`-branches, `ORDER BY <sort key> LIMIT :limit`. Two things compound: (1) the sort key (`student_code`/`isbn`) is not the FULLTEXT relevance order, so `EXPLAIN` shows `Using filesort` even for a fulltext-indexed lookup — confirmed against a real vocabulary term (`Guide*` matches 2,435 of 8,000 books, 30% of the table, `avg_rows_examined=833.5` in the live digest); (2) even `BM-STU-001` (no filter at all — the "control floor," `hazard: H3 (control floor)`) regressed +191%, which the search-index/filesort story alone doesn't explain, pointing at the combined-query shape itself (a single parameterized statement serving three logically distinct query shapes) rather than at FULLTEXT specifically. This directly contradicts `08-hazard-fix-specs.md`'s `IP-02` hypothesis ("an order-of-magnitude... drop... toward the Read-list SLO") — `BM-BK-001` instead grew **+461%** (2594 ms → 14558 ms p95). Worth a linked issue and a rung-4 (JFR/profiler) follow-up before this is called done; this record only reaches rung 3.
- **F3 — Harness bug found and fixed: `BM-STU-004`'s deep-page discovery was silently testing page 1, not a deep page.** `bench/scenarios/student-search.js` computed a target page from `body.totalPages`, a field `CursorPage` (Sprint 9's `IP-05`) no longer returns, and passed a now-unbound `page` query param the controller silently ignores. Fixed by walking `cursor`/`nextCursor` forward a bounded number of steps during warm-up instead (see the file's updated header comment). `BM-STU-004`'s -7% (no change) this run is consistent with v0.0's own S2 data (332 ms — the depth cost only showed up strongly at S3, which this fast-smoke pass doesn't cover), not evidence the fix is inert.
- **F4 — Harness bug found and fixed: `bench/lib/reportStats.js`'s `latestExports` picked the wrong file for `enrollment-list`.** Its prefix match (`enrollment-list-S2-`) also matches `BM-XC-003`'s `enrollment-list-S2-vu5-<timestamp>.json`-shaped sibling exports, and because `'v' > '2'` (a timestamp's leading digit) lexicographically, `.sort().reverse()` picked a single-VU-count sweep file over the real 20-VU `bench-all` run — silently substituting different numbers under the `BM-ENR-*` ids and reporting "NO DATA" for ids absent from that sweep file. Fixed by requiring the byte after the prefix to be a digit. Re-run and confirmed correct before this record was written.
- **F5 — Self-inflicted methodology error, corrected: the first `BM-XC-003` attempt was contaminated by concurrent diagnostic queries.** While diagnosing F2 (`SHOW INDEX`, `EXPLAIN`, `performance_schema` digest queries against the same MySQL container), `BM-XC-003`'s first sweep was still running in the background and produced a non-monotonic, implausible req/s curve (47.5 → 26.8 → 30.4 → 40.7 across VUs 5/10/20/40). Re-run cleanly with no concurrent activity; the table above is from that clean re-run. Recorded per `05-baseline-and-reporting.md` §4.1's "rule out the benchmark" checklist, item 1 (was the driver — or in this case, the host — saturated by something other than the load test itself).
- **F6 — `BM-STU-004` at S2 alone cannot confirm or refute `IP-05`'s core hypothesis.** v0.0's own data shows the OFFSET-depth cost was flat S1→S2 (318 ms → 332 ms) and only diverged sharply at S3 (3375 ms). This fast-smoke pass deliberately excludes S1/S3 — see this folder's `README.md` for the deferred scope. `IP-05`'s "page depth stops being a cost variable" claim needs an S1/S2/S3 re-run to actually verify, not this record.
