## Findings

- **F1 — Host was not quiet this session, unlike the protocol both this and prior records require.** `uptime` showed load averages of 3–4.6 on a host whose Colima VM is capped at 2 CPUs, with `Virtualization.framework` alone sustaining ~48% CPU from unrelated concurrent work on the machine (a code editor, this benchmarking session's own tooling). `05-baseline-and-reporting.md` §4.1's "rule out the benchmark" checklist item 1 applies directly: `BM-BK-004`, whose code this fix never touches, got measurably slower under k6 than in `156d247` — decisive evidence the book-search wall-clock numbers this session are not comparable. Student search was measured first, before contention had built up as much, and its numbers are trusted; book search (measured later, and re-attempted once with load already elevated) is not. **Action: re-run `book-search` alone on a quiet host before treating these as a formal regression-verdict record.**
- **F2 — Fix confirmed at the database level for both search paths this run targeted (student, book), independent of F1's wall-clock noise.** `performance_schema` digests show the `search` (MATCH) and `browse` (no MATCH) statements as two separate digests post-fix, each now costed for what it actually does, rather than one blended digest where the no-filter case paid for the MATCH-capable plan. This is the same rung-3 diagnostic `09-v01-vs-v00-conclusions.md` §3 used to root-cause the original regression, now applied to confirm the fix.
- **F3 — New, but pre-existing (not introduced by this fix): the book/course `browse` query's owner/scope-optional branch has the same class of problem for a fully-unfiltered first page.** `EXPLAIN` on `browse` with both the owner filter and the cursor unbound (`BM-BK-003`'s literal first page) shows `type: ALL, Extra: Using filesort` — a full table scan. Reconstructing the *pre-fix* combined query with the same literal `NULL`s and re-running `EXPLAIN` against it produces the **identical** plan, confirming this is not something this fix caused — the `(:ownerId IS NULL OR owner_id = :ownerId)` sub-clause was already structured this way before Sprint 9 touched anything, and the same optimizer limitation this fix addressed for the `MATCH` branch applies to it too. Not fixed here, deliberately — same reasoning as the plan's decision not to touch the FULLTEXT/filesort interaction: one isolated, evidenced change at a time. **Worth its own follow-up issue** (a natural `IP-12` candidate): split `browse` further into an all-rows query and an owner/scope-bound query, mirroring this fix's approach.
