# Benchmark Dashboard Strategy

The benchmark observability stack is organized into **six purpose-driven dashboards**. Each dashboard answers a different performance question, from user-facing latency to infrastructure bottlenecks and root-cause analysis.

---

# 1. Benchmark Overview Dashboard

**Purpose**

Provide a high-level view of the system's health during a benchmark run.

This dashboard should answer:

> *"Is the system performing well under the current workload?"*

### Key Metrics

* Throughput (Requests/sec)
* Latency (p95, p99)
* Error Rate
* CPU Utilization
* Memory Usage
* JVM Heap Usage
* Active Database Connections

This should be the first dashboard opened during every benchmark run.

---

# 2. HTTP & Load Testing Dashboard

**Purpose**

Visualize how the application responds to increasing workload generated by **k6**.

### Key Metrics

* Active Virtual Users (VUs)
* Requests per Second (RPS)
* HTTP Request Duration

  * p50
  * p95
  * p99
* HTTP Status Codes (2xx, 4xx, 5xx)
* Failed Requests
* Dropped Iterations
* Network Sending / Receiving Time
* Waiting Time (TTFB)

Displaying **p50, p95, and p99 on the same chart** clearly exposes tail latency as concurrency increases.

---

# 3. JVM Runtime Dashboard

**Purpose**

Monitor JVM behavior during benchmark execution.

### Heap Memory

* Used Heap
* Committed Heap
* Maximum Heap

### Non-Heap Memory

* Metaspace
* Code Cache
* Compressed Class Space

### Garbage Collection

* GC Pause Duration
* GC Pause Frequency

### Threads

* Live Threads
* Daemon Threads
* Peak Threads

### CPU

* JVM Process CPU Usage
* System CPU Usage

### Memory Allocation

* Allocation Rate
* Object Creation Rate

This dashboard helps determine whether performance degradation originates from JVM resource pressure.

---

# 4. Spring Boot Runtime Dashboard

**Purpose**

Observe Spring Boot runtime components responsible for request processing.

## Tomcat

* Busy Threads
* Current Threads
* Maximum Threads
* Request Count
* Request Processing Time

## HikariCP

* Active Connections
* Idle Connections
* Pending Connections
* Connection Acquisition Time
* Connection Usage Time

This dashboard identifies application-layer bottlenecks before requests reach the database.

---

# 5. MySQL Performance Dashboard

**Purpose**

Analyze database behavior under benchmark load.

### Query Performance

* Queries per Second
* Slow Queries
* Query Latency

### Table Access Efficiency

* Rows Examined
* Rows Sent
* **Rows Examined / Rows Sent Ratio**

### InnoDB

* Buffer Pool Hit Ratio
* Buffer Pool Usage
* Dirty Pages

### Locks

* Lock Wait Time
* Deadlocks

### Temporary Objects

* Temporary Tables
* Sort Merge Passes

A high **Rows Examined / Rows Sent** ratio is often an indicator of missing indexes, full table scans, or inefficient query execution plans.

---

# 6. Performance Correlation Dashboard

**Purpose**

Provide root-cause analysis by correlating metrics from multiple system layers.

Instead of viewing metrics independently, visualize them on a shared timeline.

### Example Timeline

```
HTTP p95 Latency
        ↓
Tomcat Busy Threads
        ↓
Hikari Pending Connections
        ↓
GC Pause Time
        ↓
CPU Utilization
        ↓
MySQL Slow Queries
```

This dashboard allows engineers to answer questions such as:

* Did latency increase because Tomcat became saturated?
* Did connection pool exhaustion cause request queuing?
* Was the latency spike triggered by long GC pauses?
* Did slow SQL queries propagate back to the application layer?

Rather than simply showing **what became slower**, this dashboard explains **why it became slower**.

# Recommended Dashboard Set

| Dashboard                   | Primary Objective                                                       | Data Source                         |
| --------------------------- | ----------------------------------------------------------------------- | ----------------------------------- |
| **Benchmark Overview**      | High-level benchmark summary (throughput, latency, errors, CPU, memory) | Prometheus + Micrometer             |
| **HTTP & Load Testing**     | Analyze workload characteristics and HTTP performance                   | k6 + Prometheus                     |
| **JVM Runtime**             | Monitor heap, GC, CPU, threads, and allocation behavior                 | Micrometer Actuator                 |
| **Spring Boot Runtime**     | Observe Tomcat and HikariCP runtime metrics                             | Micrometer Actuator                 |
| **MySQL Performance**       | Analyze SQL execution, indexing efficiency, and InnoDB behavior         | MySQL Exporter + Performance Schema |
| **Performance Correlation** | Correlate metrics across the application stack to identify bottlenecks  | Prometheus                          |

This dashboard organization follows a layered observability approach, allowing benchmark results to be analyzed from **user experience (latency and throughput)** down to **application internals (Tomcat, HikariCP, JVM)** and finally to the **database engine**, making performance investigations systematic and evidence-driven.
