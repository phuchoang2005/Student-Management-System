## Findings

- **F1 — Compared to S1, every BM-ID got slower, several substantially** (e.g. BM-BK-003 p95 4870ms→6671ms, BM-ENR-003 p95 396ms→2520ms). Given the shared confounds (F2 below and Hikari pool), this is consistent with genuine H1/H2 data-volume growth but not cleanly separable from it — same caveat as S1's F2, carried forward. Worth a proper comparison once PM-039 (Sprint 8) adds baseline-vs-run regression math and this run's pool-contention question is isolated.
- **F2 — Same across-the-board SLO breach as S1**, for the same reasons (`2026-08-26-S1-1587ed3.md` F2). Not re-litigated here in full; the short version is that this run cannot distinguish "S2's data volume makes things slower" from "20 VUs queuing on a 10-connection pool makes everything slower regardless of data volume."
- **F3 — App was not restarted between S1 and S2**, deviating from `04-workload-data-preparation.md` §5's "restart the application between scales." Chosen deliberately for speed, consistent with your direction to simplify the pipeline. Means the JVM was already warm from S1's traffic going into S2's (short) warm-up window — if anything this should make S2 look *faster* relative to a cold start, not slower, so it doesn't explain F1's regression and is noted for completeness rather than as an excuse.
