## Results — `BM-JMH-002`, AES cipher (`Cipher.getInstance` per call vs. reused)

| Variant | Cost (µs/op) |
| --- | --- |
| `encryptAsWritten` (per-call `Cipher.getInstance`) | 4.04 ± 1.49 |
| `decryptAsWritten` | 3.68 ± 1.88 |
| `encryptReusedCipher` | 0.83 ± 0.29 |

The as-written per-call JCE provider lookup costs roughly **5× more** than a reused `Cipher` instance — but both are measured in **microseconds**, next to BCrypt's **milliseconds**. Confirms `03-benchmark-scenarios.md`'s own prediction exactly: "the honest expectation is that it is dwarfed." At registration time this cost is roughly 0.004% of the BCrypt cost it runs alongside — not worth changing on this evidence alone (`01-benchmark-strategy.md` §5.1's guardrail: a JMH result alone never justifies a code change).

**Confirms the expected null result for `Credits`/`Isbn`/`StudentCode`**: single-digit nanoseconds, indistinguishable from measurement noise next to any request-level cost. `Email`'s valid-path cost (162 ns) is a real, measurable outlier against the other three — 50–80× higher — but is still five orders of magnitude below a single BCrypt hash and does not change the overall finding. See Finding F1. The invalid-input paths cost roughly 1.6–2.3 **microseconds** across all four — exception construction, not validation logic — still negligible at request scale (a rounding error next to any of this day's millisecond-scale HTTP numbers).

## Findings

- **F1 — `Email`'s valid-path construction is not free, unlike the other three value objects, though it remains negligible in absolute terms.** 162 ns vs. 2–3 ns for `Credits`/`Isbn`/`StudentCode`. `student/domain/Email.java:13`'s `Pattern` field is `static final` (no per-instance recompilation), so the extra cost is plausibly the regex *matching* itself running against a more complex pattern than the other three value objects' validation, not compilation. Still five orders of magnitude below any request-level number recorded this pass — **not worth a code change on this evidence** (`01-benchmark-strategy.md` §5.1's guardrail applies directly: a JMH result never justifies a change on its own, and nothing in the S2 records above shows registration/update latency bottlenecked here). Recorded because `03-benchmark-scenarios.md` §9 explicitly asks for the value-object result to be written down "whether or not it is noise" — this one technically isn't pure noise, even though it doesn't matter.
- **F2 — BCrypt strength 10 is confirmed as the dominant cost on both the login and registration paths.** Cross-referencing against `2026-08-27-S2-d891911.md`: `BM-STU-006` (registration) p50=315 ms against a 90.79 ms BCrypt-encode floor plus a ≈4 µs AES cost — the remaining ≈220 ms is HTTP/DB/framework overhead, not identity work. `BM-IDN-001`'s ramp shows the *concurrent* cost compounding past 1 VU (H5's real story) rather than the per-call cost changing, which this suite deliberately cannot show (JMH measures one thread's per-call cost, not contention) — the two documents are complementary, not redundant, exactly as `02-benchmark-plan.md` §3 step 8 intends ("reads best *after* step 4 has shown what BCrypt costs end-to-end").
