Exponent = ln(p95 S3 ÷ p95 S1) ÷ ln(rows S3 ÷ rows S1); ~0 is flat (cost independent of row count), ~1 is linear (proportional), notably above 1 is worse than linear. **Read "flat"/"linear" here as classifications relative to the *row-count* growth rate (1,000×–2,667× across these six tables), not as "latency didn't change"** — every one of these scenarios' absolute p95 grew substantially in real terms (e.g. `BM-STU-002` still went from 263 ms to 1.65 s); the exponent says that growth is sub-proportional to how much bigger the table got, which is the more meaningful read for a search/list endpoint. This classification still carries the same caveat `bench/scale-sweep.js` itself prints and the 2026-08-26 S1/S2/S3 records already flagged: it's built from single-repetition runs confounded with the Hikari pool-contention issue `BM-XC-003` (above) now isolates — a clean re-run of this sweep, at S1/S2/S3, with the pool confound understood, is the natural next follow-up.

## Findings

- **F1 — H6 confirmed at real severity: a 200-student burst delete rejects the majority of its cascade cleanup events, permanently.** `EVENT_PUBLICATION` (Spring Modulith's own event-publication registry) shows **568 of 801 total rows still incomplete** more than 30 minutes after the burst (cascade-delete's own drain script gave up after a 120 s timeout with 269/360 of *that run's own* events still pending; the fuller 30-minute soak afterward confirms those never resolved — rejected tasks are not retried by `ThreadPoolTaskExecutor`, they're simply dropped). **This is exactly the scenario `01-benchmark-strategy.md` H6 predicted**: "a rejection leaves publications unresolved, which the DB-level `ON DELETE` constraints cover for data but not for the event log." Confirmed the data side is genuinely safe: `books.owner_id` has `ON DELETE SET NULL` and `enrollments`/`users` have `ON DELETE CASCADE` (`V1__init_schema.sql:42,51,68`), enforced synchronously as part of the same `DELETE` statement, independent of whether the async listener ever runs. So **no student, book-ownership, or enrollment data is at risk** — but `EVENT_PUBLICATION` itself, which is Spring Modulith's audit trail of what fired, is left permanently wrong for more than two-thirds of a 200-student burst. Anything that ever comes to depend on that registry being complete (a future listener, an audit report) would see a false picture. Worth an issue: either widen `AsyncConfig`'s queue/pool for this workload shape, or accept the bound and document that bursts above roughly 50–100 students should be paginated client-side.
- **F2 — `BM-STU-007`'s confound (see the companion file's F2) persisted throughout the 30-minute soak, unchanged.** 100% of its 1,828 requests in the soak failed with the same `409 Conflict` optimistic-lock pattern, for the same reason (`bench/lib/vuShard.js`'s per-VU sharding not fully isolating targets under k6 v2.2.0's actual VU numbering). Not re-analyzed here; see the companion file. The rest of the soak's traffic (99.23% of all requests) was unaffected.
- **F3 — Second harness bug found and fixed mid-run: `bench-mixed-soak`'s `Makefile` target killed its own H7 companion script with the wrong signal.** `bench/monitor-soak.js` only saves its collected samples on `SIGINT` (see its own header comment), but the `Makefile` target stopped it with a plain `kill` (`SIGTERM` by default) — which Node terminates on immediately, without running the `SIGINT` handler. The result: **no `bench/out/monitor-soak-S2-*.json` file was ever written**, despite the script sampling correctly for the full 30 minutes. The data was recovered from the script's own `console.log` output, captured in this run's raw log (56 samples, one per ~32 s) — see the Saturation table above and F5. Fixed in `Makefile` (`kill` → `kill -INT`, plus a 1 s grace period for the write to flush) so a future run doesn't need this recovery step. Like the companion file's F1, this is a harness bug, not an application defect, and was never caught before because this is the first time `bench-mixed-soak` has been run to completion.
- **F4 — Hikari/session saturation signals were captured live for the first time this pass, via H8's actuator surface (logged in as the `SYSTEM_ADMINISTRATOR` cohort account and polling `/actuator/metrics/hikaricp.*` every 30 s during the soak).** This is the first run in this project's benchmark history where a saturation signal was measured directly rather than inferred — closing the gap `2026-08-26-S1-1587ed3.md` Finding F3 flagged for host CPU and extending the same practice to the connection pool. GC pause metrics were available via the same mechanism but not sampled this pass (candidate follow-up).
- **F5 — H7's heap-bytes-per-session curve is not a clean growth signal, and should be read carefully.** Session count *rose* from 224 to a peak of ~253 over roughly the first 20 minutes (consistent with `maximumSessions(SessionLimit.UNLIMITED)` — `SecurityConfig.java:125` — placing no cap, so concurrent distinct logins across the soak's 45 VUs accumulate), then *fell* sharply to 47 by the 30-minute mark. Two plausible mechanisms, not distinguished by this run: Spring Boot's default 30-minute session timeout reclaiming the earliest-created sessions as the soak's own 30-minute window closes, or k6's ramp-down curtailing which VUs are still active (and therefore authenticated) right at the tail. Because `heapBytesPerSession` is `heapUsed ÷ sessionCount`, the late-run figures (up to 17.2 MB/session) are inflated by the shrinking denominator combined with ordinary GC-driven heap fluctuation, not a real per-session cost — **the more trustworthy number from this run is the early/mid-soak range, roughly 1.7–2.3 MB/session** (the first ~15 samples, before the decline began), which is itself much larger than a bare `HttpSession` should cost and is worth a dedicated JFR heap histogram in a future pass rather than trusting this actuator-metric proxy alone.
