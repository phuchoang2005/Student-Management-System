## Summary

v0.0's benchmark pass (`docs-v00/Benchmark/`) read the shipped implementation, named eight specific
hazards by file and line, then measured them under k6 load against a real MySQL 8 database. v0.1 is
the fix for those eight — no feature changed, only how efficiently each one runs under concurrent
use. See [What's new in v0.1](../README.md#whats-new-in-v01) in the root README for the customer-facing
version of this summary.

## Highlights

- **Connection pool resized.** HikariCP was left at its untuned default of 10 connections, which
  produced a hard concurrency ceiling at exactly 10 simultaneous users. Raised and tuned against the
  database's real headroom — the ceiling is gone, not just moved.
- **Enrollment listings batched.** Course/student lookups for a page of results were resolved one
  row at a time; now resolved in a single query per page. **50–78% faster**, and the cost no longer
  scales with page size.
- **Search indexed.** Student/book/course search scanned the full table twice per request (once for
  results, once to count them). Replaced with a MySQL `FULLTEXT` index and purpose-built queries.
- **Keyset (seek) pagination** replaces `OFFSET`/`LIMIT` for deep list pages, so page depth stops
  being a cost variable.
- **A regression, found and fixed before release, not smoothed over.** The first verification pass
  on the search fix caught a 461% p95 regression on the worst-case search query — the combined
  search/browse query had been optimized for one access pattern at the cost of the other. Root-caused
  via `EXPLAIN` and `performance_schema` digests, split into two purpose-built queries, and
  re-verified clean.
