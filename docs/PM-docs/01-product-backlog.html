Project Management Documentation — Part 1 of 4

Part 1 Product Backlog  →  Sprint Plan  →  Scrum Artifacts  →  Sprint Backlog

Turns the completed specification (BA-docs, SA-docs, Testing) into a ranked, estimated backlog. No new business rules, roles, or endpoints are introduced here — every functional item reuses the existing US-x.x / UC-x IDs verbatim from user-stories.md and use-cases.md. Items with no user story (build/tooling prerequisites) are numbered PM-0xx and sourced from the gaps already flagged in Testing/02-test-plan.md §5 and §8.

1. How to read this backlog

  • Epic — one of the 5 Spring Modulith modules (student, course, book, enrollment, identity) plus shared/platform and a final cross-cutting/hardening epic, matching the module boundaries fixed in SA-docs/02-component-diagram.md.
  • Item — either a user story ID (US-x.x, acceptance criteria live in user-stories.md and are not restated here) or a platform item (PM-0xx).
  • Priority — MoSCoW. Nearly everything is Must because Testing/README.md already commits to covering all 23 UCs with at least one test case each; items marked Should are explicitly flagged as recommended-not-required in Testing/02-test-plan.md §8.
  • Estimate — ideal developer-hours, not story points. The confirmed delivery model is a solo developer, so a shared team velocity in points has no meaning here; hours are a sizing input for 02-sprint-plan.md, not a commitment.
  • Sprint — which sprint the item is pulled into, per the sequence fixed by Testing/02-test-plan.md §2 (dependency order: shared → student+identity provisioning → course → book → enrollment → identity auth → cross-cutting).
