## Findings

- **F1 — Blocking harness bug found and fixed: `bench/seed/generate.js` seeded every bulk-inserted row's `version` column as `0`.** `StudentRow.java`'s own `@Version long version` field comment explains why that's wrong: Spring Data JDBC's default `IsNewStrategy` for a *primitive* version field treats `0` as "never persisted," so the app's first `UPDATE`/`DELETE` against any bulk-seeded row was issued as an `INSERT` and collided on the row's own primary key (`DuplicateKeyException`, confirmed via full stack trace through `JdbcAggregateTemplate` → `DefaultDataAccessStrategy.insert`). This is **not an application defect** — the app's own registration flow (`BM-STU-006`) always leaves `version=1` after a real first save, confirmed by direct query — it's a data-generation bug in the benchmark harness, invisible until the P1 write scenarios were run for the first time (which is exactly why nobody had seen it: Sprint 7's read-only scenarios never write, and Sprint 8 built the write scenarios but never ran them end-to-end before now). Fixed by changing all four bulk-inserted tables' `version` literal from `0` to `1`, reseeded, and every write scenario except `BM-STU-007` (F2) came back at 0% errors. The first (failed) attempt's raw export is not included above; only the post-fix run is.
- **F2 — `BM-STU-007` (student update), 46.95% error rate, all confirmed `409 Conflict` optimistic-lock rejections, not a defect.** Directly reproduced outside the k6 run: firing 5 truly concurrent `PUT`s at the same student row from a valid session produces exactly 4×`409 {"message":"Student ... was modified concurrently"}` and 1×`200` — the app's optimistic locking is working exactly as designed. `bench/lib/vuShard.js` partitions students per-VU specifically to prevent any two VUs from ever targeting the same row, and it demonstrably works for `BM-CRS-004` in the same file (0% errors, same sharding mechanism) — but not for `BM-STU-007`. The leading hypothesis is that k6 v2.2.0 does not allocate contiguous, low VU-id numbers per scenario stage the way `bench/lib/vuSession.js`'s header comment assumes, so `shardFor`'s `(vuNumber - 1) % totalVus` partition can collide across scenario stages that use different VU counts. **`BM-STU-007`'s latency numbers above should not be read as a clean Write-simple measurement** — they're a mix of genuine 200s and fast-failing 409s. A worthwhile follow-up: widen `MAX_SHARD_VUS` well beyond any single file's peak VU count, or shard by a hash of `__VU` instead of a raw modulo, and re-run.
- **F3 — H4's batch cost curve is not clean-linear.** `BM-ENR-006`→`BM-ENR-007` (1→10 courses, 10×) grew p95 only 480→663 ms (1.4×) — sub-linear, plausibly because the batch endpoint's fixed per-request overhead dominates at small N. `BM-ENR-007`→`BM-ENR-008` (10→50 courses, 5×) grew p95 663→2950 ms (4.4×) — close to linear, consistent with `api-specification.md`'s documented ~2N+2-statement/N-commit cost dominating once N is large enough to amortize the fixed overhead. Not a defect — `05-baseline-and-reporting.md` §5.1 is explicit that H4's cost is a deliberate, already-accepted design trade-off (partial-success durability); this number is what belongs in client-facing guidance on where to split a large batch request.
- **F4 — H5's login-ramp knee is sharp and early.** p95 goes 170 ms (1 VU) → 823 ms (10 VU, +384%) → 1.71 s (25 VU) → 3.12 s (50 VU) → 6.07 s (100 VU) — on this 4-core host, saturation is visible almost immediately past 1 concurrent login and grows roughly linearly with offered load beyond that, consistent with BCrypt strength-10 being genuinely CPU-bound (H5, by design — `01-benchmark-strategy.md` §3). No threshold is proposed for changing the work factor; this curve is the floor the Login SLO is judged against.
- **F5 — No user-enumeration timing signal.** `BM-IDN-002` (wrong password, 20 VUs) measured p95=1.35 s — in the same range as a correct-password login interpolated at 20 VUs from the ramp (between the VU10 and VU25 points, ~1.3–1.5 s). Failed and successful logins cost approximately the same, which is the secure outcome `03-benchmark-scenarios.md` was checking for. Recorded per `05-baseline-and-reporting.md` §5.1 as a successful null result — not a security finding, and not filed anywhere.
- **F6 — Host CPU was captured this run (28–100%, avg 52%), closing Finding F3 from `2026-08-26-S1-1587ed3.md`.** Peak coincides with the deliberate `BM-IDN-001` VU100 saturation step, not with any other scenario — no evidence the k6 driver itself was the bottleneck for the write/batch/lower-VU-ramp scenarios.
