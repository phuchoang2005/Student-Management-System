## S1 → S2 → S3 curve (`BM-XC-004`'s question, answered informally)

The full `BM-XC-004` scenario (all six P0 ids run identically at all three scales as one cross-cutting measurement) is Sprint 8 (`03-benchmark-scenarios.md` §8, PM-036). This is not that — it's the same six numbers read off the three independent per-scale records already produced. p95, by row count:

| BM ID | S1 (rows) | S2 (rows) | S3 (rows) | Shape |
| --- | --- | --- | --- | --- |
| BM-STU-002 | 263 ms (50) | 263 ms (5,000) | 1652 ms (50,000) | Flat S1→S2, then a large jump into S3 |
| BM-STU-004 | 318 ms (50) | 332 ms (5,000) | 3375 ms (50,000) | Same shape |
| BM-BK-001 | 2282 ms (100) | 2594 ms (8,000) | 8571 ms (80,000) | Mild growth S1→S2, then a large jump |
| BM-CRS-001 | 344 ms (20) | 440 ms (300) | 3564 ms (1,000) | Mild growth, then a large jump |
| BM-ENR-002 | 320 ms (~150) | 670 ms (30,000) | 1356 ms (~400,000) | Roughly doubles at each step — closer to steady growth |
| BM-ME-002 | 218 ms (~150) | 433 ms (30,000) | 714 ms (~400,000) | Same steady-growth shape as BM-ENR-002 |

**Read this shape with real caution, not as a clean H1/H2/H3 curve.** Every number here carries the same pool-contention confound as the S1 and S2 records' Finding F2 (20 VUs against a 10-connection Hikari pool), *and* S3's numbers additionally cross the point where the dataset stops fitting the 128 MB buffer pool (`04-workload-data-preparation.md` §1 says this is expected and is the point) — two effects large enough that this single-repetition run cannot separate them from genuine per-row query cost. The search/list-page scenarios (STU-002/004, BK-001, CRS-001) show a sharper S2→S3 jump than the enrollment/course-lookup scenarios (ENR-002, ME-002), which is at least directionally consistent with H1's leading-wildcard-scan cost (linear in table size, ×2 per request) being more sensitive to row count than H2's per-page N+1 (bounded by page size regardless of table size) — but that's a hypothesis to verify with a properly isolated run, not a conclusion this record can support on its own.

## Findings

- **F1 — The curve is informative but confounded**, per the table above. Treat this run as "a first look," not as evidence for or against any specific hazard's growth shape.
- **F2 — Same protocol/host caveats as S1 and S2** (`2026-08-26-S1-1587ed3.md` F1-F3): 1-repetition protocol, no host-CPU capture, Hikari pool contention plausible across every endpoint.
